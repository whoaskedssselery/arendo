## 2. Порядок работ

1. Бэкенд поднимает рабочий API (минимум: вход, каталог, карточка помещения, календарь, создание и отмена аренды, завершение аренды).
2. Фронтенд собирает экраны (каталог, карточка с календарём, мои аренды) и подключает к API.
3. Бэкенд и фронтенд делают оптимизацию и кэширование, снимают результаты «до» и «после».
4. Тестировщик проверяет, что всё работает, пишет Test_Report.
5. Аналитик пишет три отчёта по готовым данным, тимлид собирает презентацию и финальный отчёт.

## 3. Задачи по ролям

### Backend

Нужно сдать: работающий API с оптимизациями, доказательства (скрины и логи) для презентации, помощь тимлиду на защите.

1. Поднять NestJS-проект, подключить PostgreSQL, выполнить `db/01_schema.sql`, `02_logic.sql`, `03_seed.sql`. Спецификация: `docs/api/openapi.yaml`.
2. Реализовать минимальный набор эндпоинтов (см. выше), вызывающий функции БД (`fn_cancel_booking`, `fn_complete_booking`, `fn_room_busy_slots`).
3. **Паттерны** (применить в коде и уметь показать файлы):
   * MVC и модульность: модули NestJS `auth`, `rooms`, `bookings`, `reviews`; контроллер, сервис, репозиторий, DTO;
   * Singleton: сервисы NestJS (единственный экземпляр через DI), единый клиент БД и кэша;
   * Repository: доступ к БД только через репозитории;
   * по желанию Strategy (расчёт цены: почасовой и суточный тариф) и Observer (событие «аренда завершена» → расчёт штрафа и рейтинга).
4. **Анализ производительности:** включить логирование медленных запросов, на тестовых данных (10 000+ помещений, 100 000+ аренд) сделать `EXPLAIN (ANALYZE)` каталога и календаря.
5. **Индексы:** основные уже есть в `db/01_schema.sql` (GiST по периоду, частичные индексы). Проверить планы, при необходимости добавить индексы под реальные медленные запросы. Результат: «до» и «после» в миллисекундах.
6. **Кэширование на сервере:** кэшировать каталог (короткий TTL 30–60 с), список категорий (долгий TTL, часы), карточку помещения (TTL 1–5 мин). Календарь кэшировать коротко (10–30 с) и сбрасывать при создании или отмене аренды. Сделать инвалидацию при изменении помещения. Реализация: `@nestjs/cache-manager` (память) или Redis.
7. **Оптимизация передачи данных:** пагинация, выбор только нужных полей (не `SELECT *`), сжатие ответов (gzip), заголовки `ETag` и `Cache-Control`.
8. Собрать для презентации: скрины `EXPLAIN` до и после, время ответа API без кэша и с кэшем, логи попаданий в кэш.
9. Подготовиться отвечать на вопросы кафедры, части 1–4 в `docs/qa/` и вопросы по новым темам (раздел 6).

7. Скрины работающего интерфейса для презентации (каталог, календарь, мои аренды, кабинет владельца).

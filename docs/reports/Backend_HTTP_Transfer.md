# Передача данных в HTTP API Arendo

Замеры задачи №11 сравнивают HTTP-ответы до и после включения gzip и политики перепроверки кэша. Для исходного прогона использован коммит [f711509](https://github.com/whoaskedssselery/arendo/commit/f711509f5c64ef3a4f843cb7a67024e2d59d117c).

## Условия

Оба прогона выполнены локально на одной базе PostgreSQL 15.20 в Docker с 12 004 помещениями и 120 006 арендами. Клиент использовал Node.js 25.8.0, `Accept-Encoding: gzip` и одно соединение HTTP/1.1 keep-alive. Перед 30 последовательными измерениями каждого сценария выполнено пять запросов для прогрева. Время измерено от начала запроса до получения тела, размер указан для переданного тела в байтах без HTTP-заголовков.

## Размеры и время ответов

| Сценарий | Тело до → после, байт | Медиана до → после, мс | P95 до → после, мс |
| --- | ---: | ---: | ---: |
| Каталог, 20 помещений | 8 828 → 982 | 0,882 → 1,247 | 1,260 → 2,541 |
| Каталог, 100 помещений | 43 993 → 3 669 | 1,839 → 2,164 | 2,216 → 2,503 |
| Категории | 675 → 351 | 0,561 → 0,688 | 0,705 → 0,949 |
| Карточка помещения | 464 → 464 | 0,633 → 0,655 | 0,982 → 0,752 |
| Каталог, условный запрос с совпавшим ETag | 0 → 0 | 1,517 → 1,735 | 1,993 → 2,133 |

У страницы из 100 помещений тело сократилось на 91,7%, медиана по локальной сети выросла на 0,325 мс. Для карточки размером 464 байта применяется передача без сжатия. SHA-256 декодированных ответов совпал в каждом сценарии. [Замеры до](benchmarks/http-before.txt), [замеры после](benchmarks/http-after.txt)

## Реализация и проверка

- Каталог использует `page` и `pageSize`. По умолчанию на странице 20 помещений, максимум 100. SQL явно перечисляет поля на всех этапах. `created_at` участвует в сортировке по новизне и остаётся внутри запроса. [RoomsRepository](../../backend/src/rooms/rooms.repository.ts)
- Успешные публичные JSON-ответы размером от 512 байт сжимаются, если клиент поддерживает подходящую кодировку. Для gzip используется уровень 4. Заголовок `Vary: Accept-Encoding` разделяет варианты передачи. [Настройка сервера](../../backend/src/main.ts), [документация Express compression](https://expressjs.com/en/resources/middleware/compression/)
- Публичные ответы возвращают слабый `ETag` и `Cache-Control: public, no-cache`. Клиент может сохранить ответ и перепроверить его с `If-None-Match`. При совпадении сервер возвращает `304` без тела и сохраняет `ETag`, `Cache-Control` и `Vary`. Ответы с токенами и профилем используют `no-store`. [Контракт OpenAPI](../api/openapi.yaml), [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5), [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)
- Проверено на HTTP-маршрутах, что запросы со старым `ETag` получают изменившуюся цену в карточке и каталоге и обновлённый календарь после создания и отмены аренды.

## Воспроизведение

Подготовьте базу `arendo_benchmark` по инструкции замеров SQL, запустите backend и выполните из корня репозитория. [Сценарий подготовки базы](Backend_Performance.md#как-повторить-замер)

```powershell
node backend/benchmarks/http-transfer.mjs http://127.0.0.1:3000
```

Для замера «до» запустите backend коммита `f711509` на той же базе и передайте скрипту адрес этого сервера.

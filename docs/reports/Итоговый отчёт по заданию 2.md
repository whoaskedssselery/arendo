## 2. Что сделано

### Аналитик
* Роли и матрица прав: гость, арендатор, арендодатель, администратор (приложение Б к ТЗ).
* Требования безопасности: JWT (access 15 минут, refresh 30 дней), хэширование паролей, ограничение попыток входа, защита от OWASP Top 10, HTTPS, ограничения загрузки файлов.
* Функциональные требования ФТ-1…ФТ-3 (регистрация, вход, блокировка).

### Серверная часть
* Спецификация RESTful API в формате OpenAPI 3.0: 36 эндпоинтов в 8 группах (Auth, Rooms, Categories, Bookings, Reviews, Tenants, Blacklist, Admin). Для каждой операции описаны параметры, схемы запроса и ответа, коды ошибок и требование авторизации. Спецификация проходит автоматическую валидацию.
* Единый формат ошибок и коды ответов: 401, 403, 404, 409 (конфликт периода или статуса), 422 (валидация), 429.
* Выбран метод аутентификации: email и пароль, JWT access-токен и refresh-токен с ротацией и отзывом.
* Подготовлены таблицы `users` (роль, статус, хэш пароля) и `refresh_tokens` (хэш токена, срок, отзыв).
* Авторизация спроектирована как RBAC по ролям плюс проверка владения ресурсом.

### Клиентская часть
* Список эндпоинтов по ресурсам, сгенерированный из спецификации, чтобы не расходился с контрактом.
* Макеты экранов входа и регистрации, кабинетов по ролям, администрирования.

### Тестировщик
* Подготовлены сценарии проверки безопасности (описаны в ответах кафедре, часть 4): доступ без токена, чужие ресурсы, подделанный и просроченный токен, инъекции, повторное использование refresh-токена.

## 3. Что не сделано

* **API не реализован**: нет кода контроллеров и сервисов NestJS, нет работающего сервера, поэтому Swagger UI из кода не запускался.
* **Аутентификация и авторизация не реализованы**: нет выдачи и проверки токенов, guards, ограничения частоты запросов.
* Нет автотестов API (Jest/Supertest) и тестов безопасности. Результатов тестирования API пока нет.
* Нет нагрузочного тестирования и измерений производительности API.
* Нет интеграции клиента с API, нет Postman-коллекции.
* Нет отдельного чек-листа API (есть только чек-лист БД).

## 4. Проблемы и решения

| Проблема | Решение |
|---|---|
| Как оформить действия над ресурсом (отмена, завершение аренды) | `POST /bookings/{id}/cancel` и `/complete` как операции смены состояния, а не CRUD |
| Расхождение списка API и документации | Список эндпоинтов генерируется из `openapi.yaml` скриптом |
| Ошибки синтаксиса YAML в спецификации | Автоматическая валидация, исправлено |
| Хранение токенов | В базе хранятся только хэши refresh-токенов; refresh планируется в httpOnly-cookie |

## 8. Ответы на вопросы кафедры (кратко)

**API.** 36 эндпоинтов, методы GET, POST, PATCH, DELETE. Документация: OpenAPI 3.0 с параметрами, схемами, кодами ошибок и схемой безопасности. Инструменты: NestJS с `@nestjs/swagger`, class-validator, Jest и Supertest. Безопасность: JWT, роли, проверка владения, валидация, ограничение частоты, HTTPS. Масштабирование: пагинация, фильтры на сервере, stateless-сервер. Реализация в коде — в плане.

**Аутентификация и авторизация.** Метод: email и пароль, JWT access (15 минут) и refresh (30 дней, ротация, хранится хэш). Угрозы и меры: подбор пароля (ограничение попыток), кража токена (короткий срок, HTTPS, ротация), XSS и CSRF (httpOnly и SameSite), повышение прав (проверка роли на сервере). Авторизация: RBAC плюс проверка владения ресурсом, матрица прав в ТЗ. Результатов тестов безопасности пока нет, они появятся после реализации.

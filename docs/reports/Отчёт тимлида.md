## 2. Что сделано (по ролям)

### Аналитик
* Составлено ТЗ по структуре ГОСТ 34.602-2020: 9 разделов, 25 функциональных требований (ФТ-1…ФТ-25), роли и матрица прав, критерии приёмки, требования безопасности и надёжности, формулы стоимости и штрафа.
* Проверены сущности схемы БД на соответствие ТЗ: все 12 таблиц покрывают функции ФТ-1…ФТ-25 (аренда, статусы, календарь, отзывы, штрафы, чёрный список).
* Уточнены бизнес-правила: переходы статусов, порог просрочки 15 минут, штраф 1,5 × ставка, автобан после третьей просрочки.

### Серверная часть (проектирование БД)
* Спроектирована схема PostgreSQL: 12 таблиц, 6 типов-перечислений, 2 представления, 10 триггеров, 7 функций-операций; нормализация до 3НФ.
* Двойное бронирование исключено на уровне СУБД (ограничение EXCLUDE по диапазону времени).
* Статусы привязаны ко времени: нельзя активировать до начала, нельзя отменить или изменить завершённую аренду.
* Написаны скрипты создания, бизнес-логики, тестовых данных и примеры запросов (вставка, обновление, выборка, удаление).
* Составлена спецификация REST API: 36 эндпоинтов в формате OpenAPI 3.0 (проходит валидацию).

### Клиентская часть (проектирование)
* Макеты делает фронтенд (в работе); подготовлен список экранов и API.
* Составлен список API по экранам (`docs/api/endpoints.md`, генерируется из OpenAPI).

### Тестировщик
* Составлен чек-лист БД из 9 разделов (62 проверки).
* Написаны автотесты БД: 34 проверки, последний прогон — 34 пройдено, 0 провалено.

## 3. Что не сделано

Честно:

* **Серверная часть на NestJS не реализована**: нет кода контроллеров, сервисов, аутентификации JWT и авторизации по ролям (есть только проект и спецификация).
* **Клиентская часть на React не реализована**: есть только макеты (статические HTML-страницы), нет интеграции с API.
* Макеты не перенесены в Figma; нет макетов мобильной версии отдельно (адаптивность описана в ТЗ).
* БД проверена на PGlite (PostgreSQL-совместимое ядро), но **не на настоящем сервере PostgreSQL**; 25 пунктов чек-листа (ручные) ещё не проверены (нагрузка, конкурентность, бэкап, права ролей).
* Нет Docker Compose, миграций (пока обычные SQL-скрипты), CI.
* Нет нагрузочных, интеграционных и E2E-тестов; нет руководства пользователя.
* ТЗ не согласовано с кафедрой; ФИО и сроки этапов нужно заполнить.

## 4. Проблемы и решения

| Проблема | Решение |
|---|---|
| Исполнители не приступили к работе в срок | Подготовлены проектные артефакты (ТЗ, схема БД, API, макеты, чек-лист), от которых можно сразу начинать реализацию; задачи распределены по ролям (раздел 5) |
| Как гарантировать отсутствие двойного бронирования при параллельных запросах | Ограничение EXCLUDE USING gist на уровне БД вместо проверки только в приложении |
| Как связать статусы со временем и запретить отмену завершённой аренды | Триггер допустимых переходов статусов + планировщик `fn_sync_booking_statuses()` раз в минуту |
| Дублирование данных в отзывах (быстрая выборка) может привести к несогласованности | Составной внешний ключ `(booking_id, room_id, tenant_id)` |
| Ошибки в бизнес-логике триггеров, обнаруженные при тестировании | Исправлены (общий триггер отзывов, порядок проверок), добавлены автотесты |

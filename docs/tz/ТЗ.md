## 2. Цели и назначение создания системы

### 2.1 Назначение системы

Система предназначена для публикации помещений, поиска и аренды помещений на выбранный период, контроля занятости, учёта состояния аренд, а также учёта добросовестности арендаторов (штрафы, рейтинг, чёрный список).

### 2.2 Цели создания системы

1. Исключить двойное бронирование: помещение не может быть арендовано двумя арендаторами в пересекающиеся периоды.
2. Дать пользователю наглядный календарь занятости (свободные дни и время) по каждому помещению.
3. Автоматизировать контроль статусов аренды и расчёт штрафов за просрочку возврата.
4. Сформировать прозрачную репутацию помещений (отзывы) и арендаторов (общий рейтинг, чёрный список).
5. Сократить время владельца на обработку аренд и учёт клиентов.

### 2.3 Критерии достижения целей

| Цель | Критерий |
|---|---|
| Исключение двойного бронирования | 0 пересекающихся активных аренд при 100 параллельных запросах на один слот |
| Календарь занятости | Календарь месяца загружается не дольше 1 с |
| Автоматизация статусов | Смена статуса «Ожидает → Активно» происходит не позднее 1 минуты после начала аренды |
| Штрафы | Штраф за просрочку рассчитывается автоматически при приёмке помещения |

## 3. Характеристика объектов автоматизации

### 3.1 Краткие сведения об объекте автоматизации

Объект автоматизации — процесс сдачи помещений в аренду на ограниченный период и взаимодействие владельцев помещений с арендаторами.

### 3.2 Описание процесса

1. Владелец регистрируется и публикует помещение (категория, фото, цена, описание).
2. Арендатор находит помещение через каталог (фильтры по категории, цене, вместимости, свободному периоду), просматривает календарь занятости и отзывы.
3. Арендатор создаёт аренду на выбранный период; аренда получает статус «Ожидает».
4. В момент начала периода аренда автоматически становится «Активно».
5. После использования владелец принимает помещение и завершает аренду; если возврат позже окончания периода более чем на 15 минут, начисляется штраф.
6. Арендатор оставляет отзыв о помещении, владелец оценивает арендатора.
7. При систематических нарушениях арендатор попадает в чёрный список.

### 3.3 Условия эксплуатации

Система эксплуатируется как веб-сервис в сети Интернет, доступ — через современные браузеры (Chrome, Firefox, Edge, Safari последних двух версий), в том числе с мобильных устройств.

## 4. Требования к системе

### 4.1 Требования к системе в целом

#### 4.1.1 Требования к структуре и функционированию

Система — трёхзвенное веб-приложение:

* клиентская часть — одностраничное приложение (SPA) на React;
* серверная часть — REST API на Node.js (NestJS), документация OpenAPI 3;
* база данных — PostgreSQL 15+.

Подсистемы: аутентификации и авторизации; каталога помещений; календаря и аренд; отзывов и рейтингов; штрафов и чёрного списка; администрирования; планировщика (фоновая смена статусов).

Режим функционирования — круглосуточный, плановые работы вне часов пиковой нагрузки.

#### 4.1.2 Роли пользователей

| Роль | Возможности |
|---|---|
| Гость | Просмотр каталога, карточек, календаря, отзывов; регистрация и вход |
| Арендатор | Создание и отмена своих аренд, просмотр истории и штрафов, отзывы о помещениях |
| Арендодатель | Управление своими помещениями, фото, ценами и закрытием периодов; приём помещений; просмотр карточек арендаторов; оценка арендаторов; личный чёрный список |
| Администратор | Управление категориями и пользователями; глобальные блокировки; снятие штрафов и банов; просмотр всех данных |

#### 4.1.3 Показатели назначения

* Поддержка не менее 500 одновременных пользователей и 50 запросов в секунду.
* Каталог: время ответа API не более 500 мс при 10 000 помещений (95-й перцентиль).
* Календарь занятости: ответ не более 1 с.

#### 4.1.4 Требования к надёжности

* Целостность данных — транзакции; защита от двойного бронирования на уровне СУБД (ограничение EXCLUDE).
* Доступность — не менее 99 % в месяц.
* Резервное копирование БД — ежедневно, хранение 14 дней; восстановление — не более 4 часов.

#### 4.1.5 Требования безопасности и защиты информации

* Аутентификация по email и паролю; пароли хранятся только в виде хэша (bcrypt/argon2); минимальная длина пароля — 8 символов.
* Доступ к API по JWT (access — 15 минут) и refresh-токену (30 дней, хранится хэш, ротация, отзыв при выходе).
* Ролевая авторизация (RBAC) на каждый защищённый маршрут + проверка владения ресурсом (владелец управляет только своими помещениями, арендатор видит только свои аренды).
* Защита от OWASP Top 10: параметризованные запросы, валидация входных данных, экранирование вывода, CORS по белому списку, заголовки безопасности (Helmet), ограничение частоты запросов (rate limiting; вход — не более 5 попыток в минуту с одного IP), ограничение размера и типа загружаемых файлов (jpeg/png/webp, до 5 МБ).
* Передача данных — только по HTTPS (TLS 1.2+).
* Персональные данные (ФИО, email, телефон) обрабатываются в соответствии с 152-ФЗ; доступ ограничен ролями; пароли и токены не попадают в логи.
* Ведётся журнал смены статусов аренд и действий администратора.

#### 4.1.6 Требования к эргономике и технической эстетике

* Адаптивный интерфейс (от 360 px), русский язык.
* Состояния «загрузка», «пусто», «ошибка» на каждом экране; понятные сообщения об ошибках под полями формы.
* Цветовая индикация статусов аренды и календаря; контрастность по WCAG AA.

#### 4.1.7 Требования к эксплуатации, обслуживанию и ремонту

Развёртывание в контейнерах (Docker Compose); конфигурация через переменные окружения; миграции БД версионируются; логи в структурированном формате.

#### 4.1.8 Требования к защите от влияния внешних воздействий и патентной чистоте

Используются только свободное ПО с разрешительными лицензиями (MIT, Apache 2.0, BSD, PostgreSQL License).

#### 4.1.9 Требования к стандартизации и унификации

REST-архитектура, OpenAPI 3.0, формат дат ISO 8601 (UTC), единый формат ошибок, кодировка UTF-8.

### 4.2 Требования к функциям (задачам), выполняемым системой

#### 4.2.1 Аутентификация и профиль

* ФТ-1. Регистрация с выбором роли «арендатор» или «арендодатель»; уникальность email без учёта регистра.
* ФТ-2. Вход, обновление токена, выход, получение профиля.
* ФТ-3. Заблокированный пользователь не может войти.

#### 4.2.2 Категории и помещения

* ФТ-4. Категории помещений с названием, описанием, фото и ориентировочной ценой за час (управляет администратор).
* ФТ-5. Арендодатель создаёт, редактирует и деактивирует помещение: название, описание, адрес, площадь, вместимость, цена за час и (необязательно) за сутки.
* ФТ-6. Загрузка и удаление фото; одно главное фото.
* ФТ-7. Каталог с фильтрами: категория, диапазон цены, вместимость, текстовый поиск, свободность в заданный период; сортировка по цене, рейтингу, новизне; пагинация.
* ФТ-8. Помещение с активными или ожидающими арендами нельзя деактивировать.

#### 4.2.3 Календарь занятости

* ФТ-9. Календарь помещения показывает занятые интервалы (аренды «Ожидает» и «Активно», закрытия владельцем) и свободные дни и время за выбранный период (неделя/месяц).
* ФТ-10. Владелец может закрыть помещение на период (ремонт, уборка) и снять закрытие. Закрыть период, на который уже есть аренда, нельзя.

#### 4.2.4 Аренда и статусы

* ФТ-11. Арендатор создаёт аренду, указывая помещение и период; система проверяет доступность и автоматически рассчитывает стоимость (почасовая цена; если задана суточная — выбирается более выгодная для клиента).
* ФТ-12. Ограничения: период не в прошлом; окончание позже начала; длительность не более 30 суток; нельзя арендовать собственное помещение; нельзя при бане или записи в чёрном списке; не должно быть пересечений.
* ФТ-13. Статусы: **Ожидает** (создана, начало в будущем), **Активно** (наступило время начала), **Завершено** (владелец принял помещение), **Отменено**.
* ФТ-14. Допустимые переходы: Ожидает → Активно (автоматически при наступлении начала); Ожидает → Отменено; Активно → Завершено; Активно → Отменено (только владелец или администратор). Из «Завершено» и «Отменено» переходы запрещены: завершённую аренду нельзя отменить, закрытую аренду нельзя редактировать.
* ФТ-15. Планировщик ежеминутно переводит наступившие аренды в статус «Активно»; активная аренда с истёкшим временем отображается как «Просрочена».
* ФТ-16. Ведётся история смены статусов (кто, когда, причина).

#### 4.2.5 Отзывы и рейтинг

* ФТ-17. Арендатор может оставить отзыв (оценка 1–5 и текст) о помещении только по завершённой аренде, один отзыв на аренду.
* ФТ-18. Владелец может оценить арендатора (1–5) по завершённой аренде своего помещения.
* ФТ-19. Рейтинг помещения — среднее отзывов; общий рейтинг арендатора — среднее оценок владельцев; в карточке арендатора также отображаются число аренд, отмен, просрочек и сумма неоплаченных штрафов.

#### 4.2.6 Информация об арендаторах, штрафы, чёрный список

* ФТ-20. Владелец видит карточку арендатора помещения: контакты, историю аренд, рейтинг, штрафы, статус.
* ФТ-21. При приёмке помещения с опозданием более 15 минут автоматически начисляется штраф: 1,5 × почасовая ставка × количество начатых часов просрочки.
* ФТ-22. Вторая просрочка арендатора приводит к автоматическому предупреждению, третья — к автоматическому бану (запрет аренды).
* ФТ-23. Администратор и владелец могут вручную добавить арендатора в чёрный список (предупреждение/бан с причиной и сроком); запись владельца действует только для его помещений, запись администратора — глобально. Ограничение можно снять (запись сохраняется как отозванная).
* ФТ-24. Штрафы можно отметить оплаченными или списанными.

#### 4.2.7 Администрирование

* ФТ-25. Просмотр списка пользователей, блокировка и разблокировка; управление категориями.

### 4.3 Требования к видам обеспечения

#### 4.3.1 Математическое обеспечение

Стоимость аренды: `ceil((окончание − начало) в часах) × цена_за_час`; при наличии суточной цены — `min(почасовая, ceil(часы / 24) × цена_за_сутки)`. Штраф: `ceil(часы просрочки) × цена_за_час × 1,5` при просрочке более 15 минут.

#### 4.3.2 Информационное обеспечение

Данные хранятся в реляционной БД PostgreSQL. Основные сущности: пользователи, токены, категории, помещения, фото, закрытия периодов, аренды, история статусов, отзывы о помещениях, оценки арендаторов, штрафы, записи чёрного списка. Схема в 3НФ описана в документе `docs/db/README.md`, скрипты — в каталоге `db/`. Все связи защищены внешними ключами, предусмотрены ограничения CHECK, уникальные и исключающие ограничения.

#### 4.3.3 Лингвистическое обеспечение

Интерфейс — на русском языке; исходный код, API и схема БД — на английском; сообщения об ошибках для пользователя — на русском.

#### 4.3.4 Программное обеспечение

Серверная часть: Node.js LTS, NestJS, TypeScript, ORM Prisma или TypeORM, class-validator, Passport JWT, Swagger. Клиентская часть: React, TypeScript, Vite, React Router, библиотека запросов TanStack Query. БД: PostgreSQL 15+. Тестирование: Jest, Supertest, Playwright. Контейнеризация: Docker, Docker Compose. Контроль версий: Git.

#### 4.3.5 Техническое обеспечение

Сервер: 2 vCPU, 4 ГБ ОЗУ, 20 ГБ SSD. Клиент — любое устройство с современным браузером.

#### 4.3.6 Метрологическое обеспечение

Не предъявляется.

#### 4.3.7 Организационное обеспечение

Роли команды: руководитель, аналитик, разработчик серверной части, разработчик клиентской части, тестировщик. Работа ведётся в Git-репозитории по схеме feature-веток и pull request с обязательным ревью.

#### 4.3.8 Методическое обеспечение

Руководство пользователя (арендатор, арендодатель, администратор), руководство по развёртыванию, описание API (OpenAPI).

## 6. Порядок контроля и приёмки системы

### 6.1 Виды испытаний

Автотесты БД и API, ручное функциональное тестирование по чек-листу, проверка безопасности (неавторизованный доступ, чужие ресурсы, SQL-инъекции, XSS), нагрузочный тест сценария «100 параллельных аренд одного слота».

### 6.2 Критерии приёмки

* Реализованы функции ФТ-1…ФТ-25; критические и высокие дефекты отсутствуют.
* Двойное бронирование невозможно (подтверждено тестом).
* Завершённую аренду нельзя отменить или изменить (подтверждено тестом).
* Документация API полная и соответствует реализации.
* Все пункты чек-листа БД выполнены.

## 7. Требования к составу и содержанию работ по подготовке объекта автоматизации к вводу системы в действие

* Подготовка начальных данных: категории помещений, учётная запись администратора.
* Настройка окружения (БД, переменные окружения, HTTPS, резервное копирование).
* Обучение пользователей: краткие инструкции по ролям.

## 8. Требования к документированию

Состав документации: техническое задание; описание базы данных (ER-диаграмма, словарь данных); спецификация API (OpenAPI); макеты интерфейса; чек-листы и отчёт о тестировании; руководство пользователя; руководство по развёртыванию; отчёты руководителя команды. Оформление — по ГОСТ 34 и требованиям кафедры.

# Часть 1. Разработка схемы и структуры базы данных

## Оценка «2»

**1. Какие типы данных и структуры данных определены?**
Идентификаторы — `BIGINT GENERATED ALWAYS AS IDENTITY`; строки — `VARCHAR` с ограничением длины и `TEXT` для описаний; деньги — `NUMERIC(10,2)` (не `FLOAT`, чтобы не терять копейки); время — `TIMESTAMPTZ` (с часовым поясом); булевы — `BOOLEAN`; рейтинг — `SMALLINT` с CHECK 1–5; роли, статусы — типы-перечисления `ENUM` (`user_role`, `booking_status`, `penalty_status`, …). Структура — реляционная: 12 связанных таблиц.

**2. Какие таблицы и поля включены?**
`users`, `refresh_tokens`, `room_categories`, `rooms`, `room_photos`, `room_blocks`, `bookings`, `booking_status_history`, `reviews`, `tenant_reviews`, `penalties`, `blacklist_entries`. Поля — в `db/01_schema.sql`, ER-диаграмма — `docs/db/README.md`. Главная таблица — `bookings` (помещение, арендатор, начало, окончание, статус, стоимость, фактический возврат).

**3. Какие основные проблемы обнаружены при разработке?**
* Двойное бронирование при параллельных запросах → решено ограничением `EXCLUDE USING gist` по диапазону времени.
* Статус аренды должен зависеть от времени и запрещать отмену завершённой → триггер допустимых переходов + планировщик.
* Отзывы дублируют `room_id/tenant_id` ради скорости → риск рассинхронизации, решено составным внешним ключом.
* Баги триггеров (общий триггер отзывов ссылался на несуществующее поле) выявили автотесты, исправлены.

## Оценка «3»

**1. Нормализация и оптимизация?**
3НФ: атомарные значения; нет частичных и транзитивных зависимостей (категория вынесена в `room_categories`, фото — в `room_photos`, штрафы — в `penalties`). Осознанная денормализация: `reviews.room_id/tenant_id` (быстрая выборка отзывов по помещению; защищено составным FK) и `bookings.total_price` (цена фиксируется на момент аренды). Оптимизация: частичные индексы (`WHERE is_active`, `WHERE status IN ('pending','active')`, `WHERE revoked_at IS NULL`), GiST-индекс по диапазону времени, индекс `(tenant_id, start_at DESC)`.

**2. Какие SQL-скрипты разработаны?**
`01_schema.sql` (таблицы, ограничения, индексы), `02_logic.sql` (триггеры, функции `fn_cancel_booking`, `fn_complete_booking`, `fn_sync_booking_statuses`, `fn_room_busy_slots`, представления `v_room_rating`, `v_tenant_stats`), `03_seed.sql` (тестовые данные), `04_queries.sql` (INSERT/UPDATE/SELECT/DELETE). **[готово]**

**3. Методы тестирования БД и результаты?**
Автотесты `db/tests/run.mjs` на PGlite: 34 проверки — ограничения (уникальность, CHECK, FK), запрет пересечений, статусы, штрафы и автобан, отзывы, календарь, использование индекса через `EXPLAIN`. Результат: 34 из 34 пройдено. Плюс ручной чек-лист (62 пунктов). Не проверено: нагрузка и конкурентность на настоящем PostgreSQL. **[готово, частично]**

## Оценка «4»

**1. Инструменты?**
PostgreSQL 15+, SQL, Mermaid для ER-диаграммы (встроена в Markdown), PGlite + Node.js для автотестов, `EXPLAIN` для планов запросов, Git. При реализации — Prisma/TypeORM миграции, pgAdmin/DBeaver.

**2. Методы оптимизации производительности?**
Индексы под реальные запросы (GiST для диапазонов, частичные индексы только по «живым» строкам — меньше размер и быстрее запись), фильтрация в БД, а не в приложении, пагинация `LIMIT/OFFSET`, представления для агрегатов, `EXPLAIN (ANALYZE)` перед вводом индекса, `ANALYZE` для статистики. В плане: кэширование календаря, keyset-пагинация при росте данных.

**3. Согласованность и целостность?**
Первичные и внешние ключи; `UNIQUE`; `CHECK` (цены > 0, `end_at > start_at`, рейтинг 1–5); `EXCLUDE` (нет пересечений аренд); триггеры бизнес-правил; составные FK; транзакции (`fn_complete_booking` блокирует строку `FOR UPDATE` и в одной транзакции меняет аренду, создаёт штраф и бан). Физическое удаление помещений и аренд запрещено — только деактивация, чтобы не терять историю.

**1. Подробно опишите процесс разработки схемы.**
1) Разобрали требования темы: календарь занятости, категории с фото и ценой, отзывы, статусы с привязкой ко времени, информация о клиентах, чёрный список и рейтинг. 2) Выделили сущности и связи (1:N помещение — аренды, 1:1 аренда — отзыв). 3) Определили роли и права. 4) Выбрали типы и ограничения. 5) Нормализовали до 3НФ и обосновали точечную денормализацию. 6) Вынесли критичные правила в БД (нет пересечений, допустимые статусы). 7) Написали скрипты и тестовые данные. 8) Покрыли автотестами, нашли и исправили ошибки. 9) Описали схему и чек-лист.

**2. Передовые методы и инструменты?**
Исключающие ограничения (`EXCLUDE USING gist`) с типом `tstzrange`; частичные индексы; составные внешние ключи для согласованности; журнал смены статусов; `GENERATED ALWAYS AS IDENTITY` вместо `SERIAL`; ENUM; `TIMESTAMPTZ`; автотесты схемы в CI.

# Часть 2. Серверная логика и бизнес-правила

## Оценка «2»

**1. Какие бизнес-правила определены?**
Нельзя арендовать занятый период; не в прошлом; не своё помещение; не при бане/чёрном списке; длительность ≤ 30 суток. Цена = часы × ставка (или суточная, если выгоднее). Статусы: Ожидает → Активно → Завершено / Отменено; завершённую отменить нельзя. Просрочка > 15 мин → штраф 1,5 × ставка за начатый час; 2-я просрочка → предупреждение; 3-я → бан. Отзыв — только по завершённой аренде, один на аренду.

**2. Какие операции реализованы и как взаимодействуют?**
Создание аренды → проверка доступности и расчёт цены → статус `pending`; планировщик → `active`; приёмка помещения (`complete`) → фиксация возврата → штраф → проверка автобана; отмена; отзывы и оценка арендатора; чёрный список. Сейчас логика реализована **в БД** (триггеры и функции) **[готово]**, сервисный слой NestJS, который вызывает эти функции и отдаёт REST, — **[план]**.

**3. Основные ошибки?**
Ошибка в общем триггере отзывов; граничный случай округления часов просрочки (тест показал 4 часа вместо 3 из-за текущего времени — исправили тест на точное время); путаница между «встык» и «пересечение» (диапазон `[)`).

## Оценка «3»

**1. Методы и средства?**
TypeScript + NestJS (модули, провайдеры, DI), PostgreSQL-функции и триггеры для инвариантов, class-validator для DTO, планировщик `@nestjs/schedule`.

**2. Какие правила реализованы и как влияют?**
Все перечисленные выше реализованы в БД. Влияние: приложение физически не может создать пересекающиеся аренды, изменить завершённую или отменить её; рейтинг клиента и баны считаются автоматически.

**3. Тестирование и отладка?**
34 автотеста БД, найдены и исправлены 4 ошибки. В плане: модульные тесты сервисов (Jest), интеграционные (Supertest), E2E (Playwright), нагрузочный сценарий «100 параллельных аренд одного слота».

## Оценка «4»

**1. Меры безопасности?**
Ролевая авторизация на уровне маршрутов (guards) и ресурсов (владелец управляет только своими помещениями); валидация входных данных; параметризованные запросы; rate limiting на вход; хэширование паролей; запрет заблокированным; журнал статусов. **[план: в коде сервиса; правила целостности — готово в БД]**

**2. Тестирование и отладка, дополнительные инструменты?**
Jest, Supertest, Playwright, логирование (структурированное), `EXPLAIN`, Postman/Swagger UI для ручной проверки.

**3. Производительность и надёжность?**
Транзакции и блокировка строки при смене статуса, идемпотентность отмены/завершения (повторный вызов даёт понятную ошибку 409), индексы, пагинация, фоновая задача отделена от HTTP-запросов, ограничение EXCLUDE защищает от гонок.

## Оценка «5»

**1. Подробно процесс разработки логики.**
Выписали правила из задания и ТЗ (ФТ-11…ФТ-24) → оформили матрицу допустимых переходов статусов → решили, что инварианты живут в БД (надёжнее любого кода приложения), а сервисы отвечают за права, DTO и ответы → написали функции операций → покрыли тестами → описали в API.

**2. Передовые методы?**
Инварианты в БД (EXCLUDE, триггеры), конечный автомат статусов, журнал изменений, разделение «инварианты — БД, политика прав — приложение», контрактное проектирование API (OpenAPI first), тестирование на уровне БД.

**3. Гибкость и масштабируемость?**
Параметры (порог просрочки 15 мин, коэффициент 1,5, лимит 3 нарушений) можно вынести в таблицу настроек; модули NestJS независимы; БД масштабируется индексами, репликой для чтения, партиционированием `bookings` по дате; календарь кэшируется; планировщик можно вынести в отдельный воркер.

# Часть 3. RESTful API и документация

## Оценка «2»

**1. Точки доступа и методы?**
36 эндпоинтов, префикс `/api/v1` (`docs/api/endpoints.md`): `POST /auth/register|login|refresh|logout`, `GET /auth/me`; `GET|POST /categories`; `GET|POST /rooms`, `GET|PATCH|DELETE /rooms/{id}`, `/rooms/{id}/photos`, `/calendar`, `/blocks`, `/reviews`; `GET|POST /bookings`, `GET /bookings/{id}`, `POST /bookings/{id}/cancel|complete|review|tenant-review`; `GET /tenants`, `/tenants/{id}`; `/blacklist`; `/penalties`; `/admin/users`. Методы: GET — чтение, POST — создание и действия, PATCH — частичное изменение, DELETE — удаление/деактивация.

**2. Уровень документации?**
Полная спецификация OpenAPI 3.0 (`docs/api/openapi.yaml`): параметры, схемы запросов и ответов, коды ошибок, требования авторизации; проходит валидацию. **[готово]**

Какой метод использовать для «действий» (cancel, complete) — выбрали `POST /bookings/{id}/cancel`, так как это операции со сменой состояния, а не CRUD; ошибки синтаксиса YAML выявила автоматическая валидация.

## Оценка «3»

**1. Инструменты?**
NestJS + `@nestjs/swagger`, class-validator, OpenAPI 3.0, Swagger UI, Postman. **[API в коде — план; спецификация — готово]**

**2. Уровень документации и элементы?**

**3. Тестирование API?**

**1. Безопасность?**

**2. Автогенерация документации?**
Спецификация пишется first-подходом и используется для генерации списка эндпоинтов (скрипт), в NestJS — декораторы `@ApiProperty/@ApiResponse` и Swagger UI; из спецификации можно сгенерировать типизированный клиент для React.

**3. Производительность и масштабируемость?**

# Часть 4. Аутентификация и авторизация

## Оценка «2»

**1. Выбранный метод и реализация?**
Email + пароль; после входа выдаются JWT access-токен (15 мин) и refresh-токен (30 дней). Пароль хранится как хэш bcrypt/argon2; refresh-токен — как хэш в таблице `refresh_tokens` (можно отозвать). В БД готово (`users`, `refresh_tokens`); логика на сервере — **[план]**.

**2. Уязвимости и угрозы?**
Подбор пароля (защита: rate limiting, блокировка), кража токена (короткий срок жизни, HTTPS, ротация refresh), XSS (не хранить токены в `localStorage`, refresh — в httpOnly-cookie), CSRF (SameSite), утечка БД (хэши с солью), повышение прав (проверка роли на сервере, не на клиенте).

## Оценка «3»

**1. Меры при реализации?**
Хэширование с солью, ограничение числа попыток входа (5 в минуту), одинаковое сообщение об ошибке для неверного email/пароля, проверка статуса `banned`, ротация и отзыв refresh-токенов при выходе.

**2. Особенности авторизации и роли?**
RBAC: `tenant`, `owner`, `admin` + проверка владения (владелец меняет только свои помещения, арендатор видит только свои аренды). Матрица прав — приложение Б к ТЗ.

**3. Тестирование безопасности?**
План: тесты на 401/403 для каждого маршрута, попытка доступа к чужим ресурсам (IDOR), SQL-инъекции в параметрах, XSS в отзывах, истёкший и поддельный токен, повторное использование refresh. Результаты — после реализации.

## Оценка «4»

**1. Передовые методы и инструменты?**
Passport/JWT, guards NestJS, argon2, httpOnly-cookie, ротация refresh-токенов с обнаружением повторного использования, OWASP ASVS как чек-лист.

**2. Производительность и масштабируемость?**
JWT проверяется без обращения к БД (stateless), поэтому сервер масштабируется горизонтально; refresh-токены — в индексированной таблице; чистка просроченных токенов по расписанию.

**3. Защита данных и ресурсов?**
HTTPS, минимум данных в токене (id, роль), секреты в переменных окружения, права БД по минимуму, журнал действий админа, пароли и токены не логируются.

## Оценка «5»

**1. Подробно про разработку?**
Выбрали токены, а не серверные сессии, — SPA + REST, горизонтальное масштабирование. Определили роли и матрицу прав по ТЗ → таблицы пользователей и токенов → эндпоинты `/auth/*` → guards → тесты безопасности.

**2. Стандарты и методологии?**
JWT (RFC 7519), OAuth 2.0 для рекомендаций по refresh, OWASP Top 10 и ASVS, принцип наименьших привилегий, «безопасность по умолчанию».

**3. Защита от известных угроз и соответствие нормам?**
Инъекции — параметризованные запросы; XSS — экранирование и CSP; CSRF — SameSite; brute force — rate limiting; IDOR — проверка владения; персональные данные — по 152-ФЗ (минимизация, ограничение доступа, шифрование каналов).

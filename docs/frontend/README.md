## Запуск

Node.js 22.12+ или 24 LTS; PostgreSQL 15+; backend по основной инструкции README.

```bash
cd frontend
npm ci
npm run dev
```

Открыть http://localhost:5173. Vite проксирует `/api` на `http://127.0.0.1:3000`.
По умолчанию используется `/api/v1`; `VITE_API_URL` позволяет указать другой базовый URL. При отдельном origin сервер должен разрешать CORS для frontend; конфигурация Nginx ниже оставляет API на том же origin.

Демо запускается **явно**: `VITE_DEMO_MODE=true npm run dev`.
Аккаунты `tenant@arendo.test`, `owner@arendo.test`, `admin@arendo.test`, пароль `Arendo123!`.
Моки реализуют интерфейс API, фильтры, состояния и мутации в памяти. После перезагрузки страницы данные сбрасываются. Ошибка настоящего API никогда не подменяется моковыми данными.

В API-режиме зарегистрируйте арендатора/владельца; пароли SQL seed — заглушки.
Администратор назначается доверенным администратором БД; публичная регистрация роли admin запрещена.

## Экраны и взаимодействия

- `/`: текстовый поиск, категории, цена, вместимость, сортировка, свободный период, пагинация. Фильтры хранятся в URL.
- `/rooms/:id`: фото, характеристики, цена, календарь месяца с началом недели в понедельник; занятые интервалы перечислены с точным временем. Жёлтый день означает наличие занятых часов, а не занятость всего дня. Выбор дня заполняет начало/конец; время можно изменить. Даты отправляются в ISO UTC, отображаются в часовом поясе устройства. Проверяются будущее начало, порядок дат и максимум 30 суток; доступность окончательно проверяет сервер.
- `/login`, `/register`: выбор tenant/owner, необязательный телефон, ограничения пароля и поля HTML-валидации; ошибки API показаны в форме.
- `/bookings`: список с фильтром статуса и пагинацией. Арендатор отменяет только ожидающую аренду; владелец может отменить активную аренду своего помещения и принять её. После завершения/отмены кнопки исчезают. Действия требуют подтверждения.
- `/owner`: приватный список собственных помещений с серверной пагинацией, добавление помещения, переход к приёмке.
- `/tenants/:id`: статистика, рейтинг, просрочки, штрафы, чёрный список; доступ owner только к арендатору его помещения либо admin.
- `/admin`: список пользователей с пагинацией, блокировка/разблокировка; изменение собственного статуса запрещено и в UI, и на сервере. Блокировка отзывает действующие сессии.

Для каждой загрузки есть состояния загрузки, ошибки с повтором и пустой результат. React экранирует пользовательский текст. Защита страниц дополняет серверные guards, а не заменяет их. Сессия хранится в sessionStorage текущей вкладки; при 401 выполняется одна общая ротация refresh-токена для параллельных запросов, после неудачи сессия удаляется. При выходе/смене пользователя Query cache очищается.

## Клиентский кэш и оптимизация

| Данные | staleTime |
|---|---:|
| Категории | 1 час |
| Каталог, включая фильтры/страницу | 45 с |
| Карточка | 3 мин |
| Календарь | 15 с |
| Список аренд | 15 с |

`request` принимает `AbortSignal` TanStack Query и передаёт его в fetch.
Поиск ждёт 350 мс; смена фильтров сбрасывает страницу. Карточка предзагружается при наведении и клавиатурном фокусе.
Создание, отмена и завершение аренды инвалидируют `bookings`, `calendar`, `rooms`, `tenants`, `penalties`; создание помещения инвалидирует все списки `rooms`.
Публичные запросы дедуплицируются TanStack Query. Инвалидация обновляет клиентский кэш, а соответствующие серверные операции сбрасывают серверный кэш.

[network-cache.json](network-cache.json) записывается браузерным тестом с настоящим API.
`coldRequests` — HTTP-запросы первого открытия каталога и карточки; `warmRequests` — новые запросы повторного просмотра тех же данных до истечения staleTime. Из них построены два изображения Network-отчёта для презентации. Это экспорт реально перехваченных запросов, не изображение DevTools и не искусственное сравнение со старой версией: предыдущего frontend в репозитории не было.
Тест отдельно проверяет один запрос при быстром вводе и отмену устаревшего поиска при искусственной задержке сети.

Повторить вручную: открыть DevTools → Network, очистить список, открыть карточку, вернуться в каталог и снова открыть её за 15 секунд. Новых запросов карточки/каталога/категорий/календаря не будет. Перезагрузка страницы создаёт новый QueryClient; это не дисковый кэш браузера.

## Статика и CDN

Десять WebP-фото демонстрационных помещений (около 50–240 КБ) лежат в `public/demo` и отдаются с кэшем на 30 дней; JS, CSS и шрифты Vite называет с хэшем. Карточки используют `loading="lazy"`.
Если фото нет или URL не работает, показывается пустая рамка «Нет фото».

Источник изображений — Unsplash (`images.unsplash.com/photo-<id>`): 1497366216548-37526070297c, 1604328698692-f76ea9498e76, 1517502884422-41eaead166d4, 1431540015161-0bf868a2d407, 1527192491265-7e15c55b1ed2, 1519389950473-47ba0277781c, 1598488035139-bdbb2231ce04, 1586023492125-27b2c045efd7, 1553413077-190dd305871c, 1586528116311-ad8dd3c8310d.

Сборка: `cd frontend && npm run build`. `dist/assets/*` — `Cache-Control: public, max-age=31536000, immutable`, HTML/SPA-маршруты — `no-cache`, API — `no-store` на reverse proxy. Готовый пример — `nginx.conf`; upstream `backend:3000` нужно разрешить через Docker network либо заменить адресом своего backend. Dockerfile собирает frontend и копирует его в Nginx. Проверка конфигурации на реальном сервере: `nginx -t`, затем `curl -I https://домен/assets/файл-с-хэшем.webp`.

Для Cloudflare:

1. Разместить Nginx/backend на сервере, подключить домен и TLS, включить проксирование DNS-записи в Cloudflare.
2. Создать Cache Rule только для `/assets/`: разрешить кэширование, учитывать заголовки origin. Не включать Cache Everything на всё приложение.
3. Для `/api/*`, HTML и SPA-маршрутов настроить bypass; не кэшировать ответы авторизации и личные данные.
4. Проверить `Cache-Control`, затем `CF-Cache-Status` на повторном запросе WebP/JS/CSS. Новая сборка создаёт новые хэши и новые URL.

[Официальные Cache Rules](https://developers.cloudflare.com/cache/how-to/cache-rules/) требуют проксируемой DNS-записи; [Origin Cache Control](https://developers.cloudflare.com/cache/concepts/cache-control/) описывает поддержку заголовков.
Подключение CDN описано; домен/аккаунт Cloudflare не менялись, попадание в реальный edge-кэш не заявляется.

## Проверки и воспроизведение

```bash
cd frontend
npm ci
npm run build
npx playwright install chromium
npm test
```

Обычный запуск поднимает отдельный Vite в деморежиме: 7 UI/E2E-проверок, 4 live-проверки пропускаются. В CI (`.github/workflows/frontend.yml`) выполняются сборка, UI-тесты и сохраняется HTML-отчёт/скрины.

Live-проверки требуют **отдельную одноразовую** PostgreSQL-базу, имя которой оканчивается на `_test`. Выполнить схему/логику/seed стандартным `db:init`, запустить backend с этой базой на 3000. Тест создаёт пользователей и помещения; для активной аренды и администратора подготавливает fixtures непосредственно в этой тестовой БД. Не запускать на рабочей базе.

```bash
# Терминал 1, frontend: production-сборка, demo выключен
npm run build
npm run preview -- --port 4174

# Терминал 2, frontend, backend уже запущен
LIVE_API=1 E2E_BASE_URL=http://127.0.0.1:4174 \
TEST_DATABASE_URL=postgresql://user:password@localhost:5432/arendo_frontend_test \
npm test -- tests/live.spec.ts
```

Backend-зависимости нужны для `pg` в live-fixtures: предварительно `cd backend && npm ci && npm run build`.
Итоги фактического запуска приведены в [Test_Report.md](Test_Report.md). Скрины `*-live.png` получены с настоящими NestJS/PostgreSQL; остальные — явно обозначенные демонстрационные макеты.

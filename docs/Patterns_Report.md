# Отчёт о паттернах проектирования в приложении Arendo

Команда №5 «ЧЕКЛИ». Тема: аренда помещения на определённый период. Аналитик: Коржнев М.Д.

## 1. Цель и подход

Цель — сделать код понятным и удобным для изменения. Паттерны выбирались под конкретные задачи: разделить обработку запросов и работу с данными, не создавать лишние соединения с базой, одинаково проверять права.

## 2. Архитектура

Клиент (React) обращается по REST API к серверу (NestJS), сервер — к PostgreSQL. Сервер разделён на модули по предметным областям.

| Модуль | Ответственность |
|---|---|
| `auth` | регистрация, вход, токены, роли |
| `rooms` | каталог, карточка, календарь, фото, закрытие периодов |
| `categories` | категории и их иконки |
| `bookings` | аренды, статусы, приёмка |
| `reviews` | отзывы о помещениях и оценки арендаторов |
| `moderation` | арендаторы, штрафы, чёрный список |
| `dashboard` | карточка арендатора, пользователи |
| `database`, `cache`, `health` | пул соединений, кэш, проверка состояния |

## 3. Применённые паттерны

| Паттерн | Где в коде | Зачем |
|---|---|---|
| MVC для REST | `rooms.controller.ts`, `rooms.service.ts`, `rooms.repository.ts`, `rooms.types.ts` | маршрут, бизнес-сценарий, данные и формат ответа разделены |
| Модульность | `app.module.ts` и модули областей | части приложения меняются независимо |
| Repository | `*.repository.ts` | SQL и транзакции собраны в одном слое |
| Singleton (через DI) | `database.service.ts`, `public-cache.service.ts` | один пул соединений и один кэш на приложение |
| Dependency Injection | конструкторы контроллеров и сервисов | зависимости передаются извне, их можно подменить |
| Decorator | `require-roles.decorator.ts`, `public-cache-headers.decorator.ts`, `date-time.decorator.ts` | права, заголовки и проверки задаются одной строкой над методом |
| Factory | `validation.pipe.ts`, `CacheModule.registerAsync` | однотипные объекты создаются в одном месте с нужными настройками |
| Guard (цепочка проверок) | `access-token.guard.ts`, `roles.guard.ts` | сначала проверяется токен, затем роль |
| Observer | `frontend/src/api.ts`, `ui.tsx`, TanStack Query | интерфейс обновляется при смене сессии и данных |
| Планировщик | `booking-status.scheduler.ts` | раз в минуту активирует начавшиеся аренды |

### 3.1. MVC и модульность

Контроллер принимает запрос и проверяет входные данные (DTO), сервис выполняет бизнес-сценарий, репозиторий обращается к базе, а функции `roomResponse` и `bookingResponse` формируют ответ. Роль представления в REST API играет JSON; экраны находятся в клиентской части.

### 3.2. Singleton

NestJS по умолчанию создаёт каждый сервис один раз на приложение. `DatabaseModule` экспортирует единственный `DatabaseService` с пулом соединений: им пользуются все модули, и он закрывается при остановке приложения. Кэш регистрируется один раз как глобальный модуль.

### 3.3. Repository

Сервисы не пишут SQL, а вызывают операции предметной области. Например, `BookingsRepository.transactionAs` открывает транзакцию и добавляет в неё пользователя, чтобы история статусов сохранила, кто их менял.

### 3.4. Decorator

Составной декоратор объединяет проверку токена и роли:

```
export function RequireRoles(...roles) {
  return applyDecorators(AllowedRoles(roles), UseGuards(AccessTokenGuard, RolesGuard));
}
```

В контроллере достаточно написать `@RequireRoles('owner', 'admin')`.

### 3.5. Observer

При входе и выходе клиент отправляет событие `session`, а компоненты, подписанные на него через `useSession`, перерисовываются. TanStack Query действует так же для данных: после аренды сбрасываются связанные запросы, и все подписанные экраны получают новые данные.

### 3.6. Правила в базе данных

Критичные правила вынесены в базу: ограничение `EXCLUDE` запрещает пересечение аренд, триггер `bookings_status_guard` разрешает только допустимые переходы статусов, функция `fn_complete_booking` в одной транзакции завершает аренду и начисляет штраф. Это не классический паттерн, но он гарантирует правило при любом способе записи.

## 4. Принципы SOLID и чистый код

* Единственная ответственность: контроллер, сервис и репозиторий решают разные задачи; кэш вынесен в отдельный сервис.
* Инверсия зависимостей: классы получают зависимости через конструктор.
* Открытость для расширения: новая функция добавляется отдельным модулем, существующие не переписываются.
* Строгий режим TypeScript (`strict`) на сервере и клиенте.
* Клиент форматируется и проверяется Biome; ошибок линтера нет, остаются предупреждения, в основном о порядке правил CSS.
* Параметризованные запросы и проверка входных данных через `class-validator`.
* Понятные имена и короткие комментарии там, где нужно объяснить причину.

## 5. Что дали паттерны

| Преимущество | Пример |
|---|---|
| Оптимизация без изменения API | запросы каталога переписаны только в репозитории |
| Кэш добавлен в одном месте | чтение обёрнуто в `PublicCache.read`, изменения вызывают `invalidate` |
| Одинаковые права доступа | один декоратор на всех защищённых маршрутах |
| Новые функции без переделки старых | отзывы и модерация добавлены отдельными модулями |
| Проверяемость | кэш тестируется отдельно, API — через интеграционные тесты |

## 6. Тестирование и рефакторинг

| Набор | Проверок |
|---|---|
| Тесты базы данных (`db/tests`) | 34 автотеста и 17 проверок на PostgreSQL |
| Модульные тесты кэша | 2 |
| Интеграционные тесты API | 14 |
| Тесты интерфейса (Playwright) | 7 в демо-режиме и 5 с настоящим сервером |

Все наборы проходят. Они запускаются в GitHub Actions при каждой отправке изменений (интерфейсные тесты с настоящим сервером запускаются локально). При оптимизации запросов результаты до и после сравнивались по SHA-256.

## 7. Проблемы и ограничения

| Проблема | Как решали или что осталось |
|---|---|
| Кэш мог вернуть данные, прочитанные до изменения | введены версии групп ключей |
| Параллельное завершение одной аренды | блокировка строки в транзакции: один запрос проходит, второй получает 409 |
| Поздние модули `reviews`, `moderation`, `room-management` написаны компактно | контроллер и репозиторий лежат в одном файле, отдельного сервиса нет |
| `categories.admin.ts` обращается к базе из контроллера | нарушает Repository, кандидат на рефакторинг |
| На сервере нет линтера и форматтера | стиль держится на строгом TypeScript и ревью |

## 8. Выводы

Основа приложения — модульная структура NestJS с разделением на контроллеры, сервисы и репозитории, общий пул соединений и декораторы доступа. Это позволило добавить кэш, оптимизировать запросы и дописать функции без переделки API. Следующий шаг — вынести SQL поздних модулей в отдельные репозитории и подключить линтер на сервере.
